Set up
  • Everything that follows happens inside a workspace: App Builder, app onboarding, surfacing, governance, workflows.
  • Apps in one workspace share roles, policies, semantic definitions and the ontology. That is what lets application two inherit what application one defined.
  • Create a workspace and invite your team. A company can run several workspaces, each with its own apps.

Migration and parallel run
  • App Builder includes a data migration step: point it at the old system and the new database, and for templates such as Salesforce and Workday it knows both data models and migrates the data. Forward-deployed engineers guide the process.
  • With the Empty template, the customer or FDE builds the migration for their source system.
  • Both systems then run in parallel and are kept in sync until cut-over. This is where most of the effort goes.
Connect to SIP

One database, used two ways

The app reads and writes its own database. SIP reads the same database in place through federated query, with no ETL, and can import data into an Iceberg store when that helps. Questions and workflow actions pass over MCP, and the app's dashboards come from SIP with each user's security applied.

How two databases are joined: attribute bindings
The attribute is the glue between sources, the same way as in Strategy today: add a column binding for each source. The ontology then builds on top of the attributes.
SIP's semantic layer is separate from a Strategy Mosaic model: one serves applications, the other BI. A sync tool can mirror a Mosaic model into SIP.
Semantic model

Objects

Every attribute, metric and fact, viewable by type, by data source or by application. An attribute has forms, relationships, display options, governance options (such as a scope for the caller), synonyms and an entity reference to the ontology. An application-level filter is coming.

Tables

The same tables view as in Strategy: how each attribute connects across tables, filterable by data source.

Hierarchy

The same hierarchy view as in Strategy: pick an attribute and see how it relates to everything else.

Readiness

Reviews the semantic layer so natural-language questions are answered well, with a recommendation for each finding that you can apply in place. It checks entity bindings, tables, relationships between attributes, and row filters on roles.

The ontology serves questions on data: it helps the AI understand what the user is asking about.

How a question travels
Question→Intent→Concepts→Walk the graph→Dynamic context→Attributes · metrics · filters→Check the policy→Generate the SQL→Answer + SQL + tables used
Same question, same SQL, same number. The AI interprets the words; the definition, the policy and the SQL come from the platform, so every app, report and agent gets the same answer, and you can read the SQL behind it.
Picking the right attributes, metrics and filters is all the AI has to do; together they are like a report template. Without the graph the AI relies on descriptions alone; walking the graph gives it the relationships too, so it picks the right objects far more reliably.
Knowledge

Classes

A class defines a business concept, like a class in object-oriented programming: Account, Support Case, SLA Agreement. Hovering a class explains it. It is the same idea Mosaic calls ontologies: concepts, not data.

Classes can have a parent. For example, Account, Contact and Lead are types of Party; Opportunity, Quote, Order and Support Case are commercial records. Each proposed class belongs to the application it was surfaced from.

Relation types

How two classes can be associated, starting from a source class. An account can be the child of another account; a customer places an order.

Entities

Instances that take on a class's properties. Several entities can share one class, and relation types connect them.

Semantic

The semantic objects (forms, attributes, metrics, facts, entities) that the business concepts connect to. Surfacing creates these links, so the AI can move from a concept to the right attribute or metric. A test pane shows how any question routes across the graph, and readiness checks extend to the knowledge graph too.

Why a graph of concepts

SIP graphs business concepts rather than individual records. Each user sees data according to their own security, so one graph of concepts serves every user and every connection, and the data itself stays governed in the semantic layer.

The ontology is designed to align with open standards such as Apache OSI, so semantic platforms and AI agents can share concepts.

Example policy. The policy screen previews which objects a new rule affects before you save it.
  • Roles: permissions such as read and write on metrics, entities and policies, and row-level security inside the role. Row filters can be an attribute condition, a manager or team scope, or a value from the user's SSO token such as region or tenant. Reads on an entity can also be delegated to the application.
  • Policies: allow, deny or require approval, based on the caller's role, a PII tag or any custom tag. Higher priority wins.
  • How it compares with Strategy: everything is driven by roles, entity access is read and write, and security filters live on the role.
  • Strategy Access (optional): the app keeps its own RBAC and publishes its permission sets; Strategy Access manages them centrally across apps, which keeps compliance simple. When enabled, an Access section manages users, groups, roles and permissions.

Processes cross apps as events and actions, with no integration code in between. The read step's output (opportunity name, stage, close date, region) fills the action's parameters, and an idempotency key makes sure the task is created once. If a step is rejected, the earlier steps are compensated.
  • Building blocks: every registered app's MCP tools, grouped by application, plus metric query, call to another LLM, LLM summary, knowledge-graph lookup, search and traverse, and notify.
  • Notify channels: email, Microsoft Teams and Slack, once a channel is registered.
  • Drag and drop steps and connect outputs to inputs. Sample workflows are deployed, but you can build any workflow.
